# 随手记 Project · 测试要求（Instructions / 强制）

> 本文件是本项目的**强制测试规范**。每次生成或修改任何生产代码时，都必须先读取并逐条遵守本文件；未满足即视为任务未完成。用户可随时更新，更新后以最新内容为准。
>
> 适用语言 / 工具链：Swift 6.3.3（Xcode 26.6），测试框架优先 **Swift Testing / XCTest**，覆盖率由 Xcode Code Coverage（`xccov`）统计。

最后更新：2026-08-11

---

## 0. 总原则

> **代码未附带通过的测试，视为未完成（No test, no merge）。**

- 每次输出生产代码，必须在同一交付物中包含对应测试代码，二者一同提交。
- 测试必须可独立执行、可自动化、无需人工介入即可判定通过/失败。
- 所有测试遵循 **FIRST 原则**：Fast、Independent、Repeatable、Self-validating、Timely。

## 1. 测试分层（测试金字塔）

| 层级 | 目标 | 建议占比 | 触发时机 |
|---|---|---|---|
| 单元测试 Unit | 隔离验证函数/方法/类型逻辑 | ~70% | 每次生成/修改函数即产出 |
| 集成测试 Integration | 验证模块间、与持久层/网络的协作 | ~20% | 涉及跨模块或外部依赖时 |
| 端到端 E2E / UI | 验证关键业务链路（记账→报表→账户→预算） | ~10% | 涉及完整用户流程时 |

优先补齐单元测试；仅当变更涉及外部依赖或跨模块契约时追加集成/UI 测试。

## 2. 单元测试生成要求

### 2.1 覆盖对象
- 每个新增或修改的 public 函数、方法、类型（含 struct/class/enum/actor），必须有对应测试用例。
- 每个用例遵循 **AAA（Arrange–Act–Assert）** 或 **Given–When–Then**，单一断言意图。

### 2.2 用例设计（须覆盖以下类别）
1. **正常路径**（Happy Path）：典型有效输入。
2. **边界值**：最小/最大、空/满、临界 ±1（金额、日期、账本数量等）。
3. **等价类划分**：每个有效/无效等价类至少 1 例。
4. **异常与错误路径**：非法入参、nil/空、类型错误、抛错与错误码、`throws` 分支。
5. **状态与副作用**：验证返回值 + 状态变更 + 交互（调用次数/顺序）。

### 2.3 命名与可读性
- 命名表达意图，如 `test_returnsError_whenAmountIsNegative` 或 `方法_场景_预期结果`。
- 无魔法数字，用具名常量；测试代码本身保持清晰。

### 2.4 隔离外部依赖
- 用 Mock/Stub/Fake（协议 + 依赖注入）隔离数据库、网络、文件系统、时间、随机数。
- 单元测试**禁止**真实网络、真实持久化、真实时钟，保证可重复。
- Swift 6 并发：涉及 actor/async 的逻辑必须有 async 测试覆盖，避免数据竞争。

### 2.5 框架约定
- 优先 **Swift Testing**（`@Test` / `#expect` / `#require`），或 **XCTest**。
- 覆盖率：`xcodebuild test ... -enableCodeCoverage YES`，用 `xccov` 导出报告。

## 3. 覆盖率要求（100%）

### 3.1 覆盖维度
- **语句覆盖 = 100%**
- **分支覆盖 = 100%**：每个 `if/else/switch/guard/三元/短路/可选解包` 的所有分支都被执行。
- 金融/金额计算等关键逻辑建议追加 **MC/DC**。

### 3.2 门禁执行
- 覆盖率由工具自动统计并作为硬性门禁，低于阈值判定失败。
- 生成后须**实际运行覆盖率工具并附报告**，不得凭空声称"已 100%"。

### 3.3 豁免机制（显式、可审计）
- 允许对自动生成代码、纯 DTO、`Codable` 样板、框架样板、不可达防御分支豁免。
- 豁免须显式标注并写明理由，禁止用豁免掩盖真实业务逻辑。

## 4. 回归测试

- **变更即回归**：任何修改后运行受影响范围的全部既有测试；关键变更跑全量。
- **零破坏原则**：新代码不得导致任何已有测试失败。
- **Bug 驱动测试**：修复缺陷时，先写一个能复现缺陷的失败测试，再修复使其通过。
- 回归结果须给出：通过/失败/跳过数量、失败用例明细。

## 5. Definition of Done（交付前逐项自检）

- [ ] 每个新增/修改的 public 单元都有对应测试
- [ ] 覆盖正常、边界、异常、等价类四类用例
- [ ] 语句覆盖率 = 100%，分支覆盖率 = 100%（或有显式豁免）
- [ ] 全部测试实际执行通过（附执行日志/报告）
- [ ] 既有回归测试全部通过，无破坏
- [ ] 外部依赖已 Mock，测试可重复、无 flaky
- [ ] 缺陷修复附带复现用测试
- [ ] 覆盖率报告与测试报告随代码一并交付

## 6. Agent 执行工作流（闭环）

```
1. 生成/修改生产代码
2. 生成配套单元测试（正常/边界/异常/等价类）
3. 运行测试 → 失败则分析修复，回到步骤 1/2
4. 运行覆盖率工具 → <100% 且无合理豁免则补用例，回到步骤 2
5. 运行受影响范围回归测试 → 破坏则修复，回到步骤 1
6. 产出：生产代码 + 测试代码 + 覆盖率报告 + 测试执行报告
7. 【MR 提交前】运行全部测试，全绿方可创建 PR（由 Hook 强制拦截）
```

> **本仓库的强制拦截**：`.claude/settings.json` 注册了 PreToolUse Hook（`.claude/hooks/pre-commit-swift-tests.sh`）。当执行 `git push` / `gh pr create` / `git commit` 前，会自动运行全部 Swift 测试（Xcode 工程用 `xcodebuild test -enableCodeCoverage YES`，SwiftPM 用 `swift test --enable-code-coverage`），测试失败则阻断提交。
> - 模拟器 destination 默认 `platform=iOS Simulator,name=iPhone 15`，可用环境变量 `SWIFT_TEST_DESTINATION` 覆盖。
> - test scheme 默认由 `xcodebuild -list` 自动探测第一个 scheme，可用环境变量 `SWIFT_TEST_SCHEME` 指定。
> - 尚无工程或本机无 Swift 工具链时（引导期）放行提交并告警，工程建立后自动生效。

## 7. 反模式禁止清单

- 只写 Happy Path，缺失异常与边界用例。
- 断言恒真的假测试（`#expect(true)`）或只调用不断言以刷覆盖率。
- 测试依赖执行顺序、共享可变状态、真实时钟/随机数导致 flaky。
- 单元测试打真实网络/持久化。
- 声称"已测试/已 100% 覆盖"却未实际运行工具。
- 为通过覆盖率删除断言或滥用豁免注解。
